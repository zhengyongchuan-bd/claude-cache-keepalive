# cache-keepalive — Claude 会话 Prompt 缓存保活

在 Claude Code 与上游网关（任何兼容 Anthropic Messages API 的网关，默认 `127.0.0.1:8080`）之间加一层很薄的中继：透明转发所有请求，记住每个会话最近一次请求；
1h 缓存的主对话空闲 50 分钟还没有新请求，就**自动**重放这次请求（只改 `max_tokens:0` + `stream:false`），
只读缓存、刷新 TTL，回来时就不用为整段上下文重写缓存；每段空闲最多 3 次，手动「停止」后整个会话不再自动保活。
也可以手动对「当前任务」开启更长的保活。页面和终端都能操作，并按真实 usage 核算心跳成本与实际节省，可用本机会话记录回测。

```
Paseo → claude-paseo-router → Claude Code ──ANTHROPIC_BASE_URL──▶ 保活中继 127.0.0.1:18110 ──▶ 本地网关 127.0.0.1:8080 ──▶ 上游
                                                                   │  内存快照：每个会话最近一次 /v1/messages（含请求头）
                                                                   │  保活计划：自动（每段空闲）/ 手动，N 次 × 间隔，按护栏停发
                                                                   │  账本：心跳 / 回来 / 冷启动 → 成本收益
                                                                   └─ /keepalive/ 页面与 API ◀── cache-keepalive CLI
```

> 本仓库来自作者本机的工具集。中继本身只依赖 Node.js ≥ 20，对任何兼容 Anthropic Messages API 的网关都适用；
> 文中提到的 Paseo 路由接入是作者自己的环境，按自己的网关替换 `CACHE_KEEPALIVE_UPSTREAM` 即可；网关唯一需要满足的是**同一会话落到同一上游账号**（会话粘性），否则心跳不会命中原缓存。

## 为什么值得做（以及什么时候不值得）

按 Anthropic 官方价目，Opus 5.5 输入 $4/M、缓存读取 $0.20/M（0.05×）、1h 缓存写入 $8/M（2×）：

| 场景（缓存前缀 C tokens） | 花费 |
|---|---|
| 不保活，停顿超过 1h 后回来：整段重写 | `C × $8/M`（C=276K 时 $2.21） |
| 一次心跳（`max_tokens:0`，只读不写、无输出） | `C × $0.20/M`（C=276K 时 $0.055） |
| 保住后回来的那次请求：读取代替重写 | 省 `C × $7.80/M`（C=276K 时 $2.15） |

一次 1h 重写约等于 39 次心跳，所以只要心跳是**纯读取**，保活几乎总是划算的；真正的风险是心跳没命中——
那一发会变成整段写入（2×），比不保活还贵。所以护栏的核心是「没命中就立刻停」。

实测（本机网关，2026-10-21）：12.8K 前缀的会话心跳 `cache_read=12822, cache_write=0, output=0`，
花费 $0.0026；网关按 `x-claude-code-session-id` 固定上游账号，原样重放请求头即可命中同一份缓存。

不值得保活的情形：隔夜/跨天的停顿（默认最多 12 次 × 50m）、上下文很小的会话、5m 缓存的长停顿（4 分钟一次，很快超过一次重写的价格）。

## 安装与接入

最小接入（CLI）：

```sh
node cache-keepalive/cli.js install     # Linux：systemd --user 服务 + ~/.local/bin/cache-keepalive
export ANTHROPIC_BASE_URL=http://127.0.0.1:18110   # 让 Claude Code 经过中继（也可写进 settings.json 的 env）
cache-keepalive list                    # 确认会话已出现在中继里
cache-keepalive start --global          # 给所有符合条件的 1h 主对话开启手动保活
cache-keepalive auto on --global        # 或让它按空闲自动保活（默认开）
cache-keepalive web                     # 页面地址：http://127.0.0.1:18110/keepalive/
```

非 systemd 平台（如 macOS）在一个终端里 `cache-keepalive serve`，其余命令照常使用。

`install` 会创建 `cache-keepalive.service`（systemd --user）并链接命令；早期安装的 `zyc-cache-keepalive.service` 会被自动迁移；接入只需让会话的 `ANTHROPIC_BASE_URL` 指向中继。

中继默认监听 `127.0.0.1:18110`，上游 `http://127.0.0.1:8080`（可用 `CACHE_KEEPALIVE_UPSTREAM` 或 `config.json` 改）。只有让会话的
`ANTHROPIC_BASE_URL` 指向中继，它才能被保活。

两个环境前提：

- **1h 缓存**：自动保活只对 1h 缓存生效。Claude Code 默认 5m，需要在 `settings.json` 里设 `"promptCacheTtl": "1h"`，
  或由你的路由注入（本机的 1h 路由已经这么做）。5m 缓存也能手动保活，但 4 分钟一次心跳通常不划算。
- **上游会话粘性**：心跳必须落到写缓存时的同一个上游账号/座位。作者的网关按会话 ID 固定账号；如果换成多账号随机轮询的
  网关，心跳可能落到别的账号上、既不命中还要新建一份缓存，这时应先确认粘性再启用。

- 任意 Claude Code：`ANTHROPIC_BASE_URL=http://127.0.0.1:18110 claude …`
- Paseo 的本地 1h 路由（`local/claude-opus-5-5-1h`、`fable-1h/claude-fable-5-1`）已接入：`claude-paseo-router` 启动任务时先探测
  `http://127.0.0.1:18110/keepalive/api/health`（0.3s），健康就走中继，否则直连 8080，不阻塞任务启动。5m 路由不变。
  - 路由会把选中的地址写进该路由共享的 `~/.cache/paseo/claude-router/local-opus-5-5-1h/settings.json`；
    实测正在运行的 Claude Code 会热加载这个 `env`，同目录下的会话随之切到中继（反之亦然）。
  - 临时停用：`touch ~/.config/cache-keepalive/paseo-route-disabled`，下一个任务启动时改回直连并写回 settings.json。
  - Fable 1h 路由的 settings.json 是手写的静态文件，路由只改写其中的 `env.ANTHROPIC_BASE_URL`，其余不动。
  - 回滚：用 `~/.local/bin/claude-paseo-router.bak-cache-keepalive-*` 覆盖回去（Fable 另有 `settings.json.bak-cache-keepalive-*`）。

另有两个便宜的 Haiku 5.5 路由（`local/claude-haiku-5-5-1h`、`local/claude-haiku-5-5`）同样经中继，
在 Paseo 模型列表里可选，适合用真实会话验证保活。

页面上的「保活执行记录」卡片按每个保活计划列出：每次心跳命中 / 未命中 / 超时的标记、读写 token、耗时、花费，以及人回来时是保住了、心跳多余、还是没人回来；点一行展开逐次心跳。

`router.js` 导出一个 Express 处理器，可以把 `/keepalive/` 挂到你自己的本地总入口下（转发到中继），可选。

## 终端用法

在任务的工作区（或 Paseo 任务内，通过 `PASEO_AGENT_ID` 精确定位）执行时，命令默认作用于「当前任务的会话」。

### 日常只需要这几条

| 命令 | 作用 |
|---|---|
| `cache-keepalive` | 当前会话：缓存剩余、自动 / 长保活状态与原因、上次心跳、能否保活 |
| `cache-keepalive list` | 所有会话一览：TTL / 前缀 / 缓存剩余 / 计划 / 自动保活；`--active` 只看有计划的，`--warm` 只看缓存有效的 |
| `cache-keepalive pin [--for 12h]` | 当前会话**长保活**（默认 12 小时，最长 48）：每段空闲都心跳到到期，人在工作时不发 |
| `cache-keepalive unpin` | 取消当前会话的长保活 |
| `cache-keepalive stop` | 停掉当前会话的一切保活：计划、长保活，并关闭它的自动保活（`auto on` 恢复） |
| `cache-keepalive off` / `on` | **总开关**：`off` 停掉所有会话的所有保活（自动 / 手动 / 长保活）且不能再开，写入配置重启后仍关；`on` 打开 |

### 自动保活（默认开）

1h 缓存的主对话空闲 50 分钟自动心跳，每段空闲最多 3 次；门槛见下一节。

| 命令 | 作用 |
|---|---|
| `auto` | 全局设置 + 当前会话的判定结果 |
| `auto on` / `auto off` | 打开 / 关闭当前会话的自动保活（`--global` 作用于全局开关；全局关闭时停掉进行中的自动计划，手动与长保活不受影响） |
| `auto set --count 3 --min-context 100k --min-turns 1 --quiet 1-8 --cooldown 2h --skip-closed on` | 改参数（写入 `config.json`，热加载）；`--clear-cooldown` 解除未命中后的全局暂停 |
| `auto reset [--global] [--clear-blocked]` | 清除会话级「已关闭」标记；`--clear-blocked` 同时解除未命中锁定 |
| `auto status --global` | 各会话自动保活状态汇总 |

### 手动计划（固定次数；一般用 `pin` 代替）

| 命令 | 作用 |
|---|---|
| `start [N \| --for 2h]` | 当前会话手动保活 N 次（1h 缓存默认 6 次 × 50m）；`--for` 按保护时长算次数；`--interval 45m`、`--max`、`--force` |
| `start --global [N \| --for 2h] [--ttl 5m\|any]` | 所有缓存仍有效的 1h 主对话一起开；已有计划的不动，重复执行安全 |
| `stop --global` | 停掉所有会话的计划与长保活，并关闭它们的自动保活（新会话仍按全局开关；要彻底停用 `off`） |
| `ping [--force]` | 立即补一次心跳（已有计划时计入次数） |

### 看数据

| 命令 | 作用 |
|---|---|
| `episodes [--days 7] [--session ID]` | 执行记录：每段保活发了几次、每次命中没有、花费、最后保住没有 |
| `stats [--days 7]` | 成本 / 收益汇总，自动 / 手动 / 长保活分开 |
| `events` | 最近事件：心跳、回来、冷启动、计划、自动、长保活、总开关 |
| `sessions [--hours 24]` | 最近经过中继的全部会话 |
| `backtest [--grid] [--session ID]` | 用本机会话记录回测自动保活 |
| `web` | 打印页面地址（`http://127.0.0.1:18110/keepalive/`） |

### 运维

| 命令 | 作用 |
|---|---|
| `install` / `uninstall` | 安装 systemd --user 服务 + `~/.local/bin/cache-keepalive` / 卸载 |
| `restart [--wait 5m]` | 等中继没有在途请求再重启（部署新代码） |
| `serve` | 前台运行中继（非 systemd 平台） |

### 常用选项

`--session ID`（≥6 位前缀）、`--cwd DIR`、`--all`（工作区全部会话）、`--global`、`--for 12h`、`--interval 50m`、`--count N`/`--max`、
`--force`、`--reason TEXT`、`--json`、`--relay URL`、`--token TOKEN`（写操作口令，默认读 `~/.local/state/cache-keepalive/control.token`）。

### 几种「关掉」的区别

| 想要 | 用 |
|---|---|
| 这个任务别再保活了 | `stop`（计划 + 长保活 + 自动都停；`auto on` 恢复自动） |
| 只取消这个任务的长保活，自动保活照常 | `unpin` |
| 今晚所有任务都别保活，明天再说 | `off`，明天 `on` |
| 以后都不要自动保活，只手动 / 长保活 | `auto off --global` |
| 停掉现在所有的，但新任务还按规则自动 | `stop --global` |

## 页面操作

`cache-keepalive web` 打印地址（默认 `http://127.0.0.1:18110/keepalive/`）。页面 10 秒自动刷新，所有判定与状态都来自中继，不另算一套。

| 区域 | 能做什么 |
|---|---|
| 顶部 | 在线状态、总开关、进行中计划数、长保活会话数、今日心跳额度；时间范围切换（今天 / 7 天 / 30 天） |
| 成本与收益 KPI | 净收益、保活节省、心跳成本（含预估部分）、ROI、命中率、待兑现、冷启动可挽救（自动策略 / 手动上限两个口径） |
| 自动保活卡片 | **全部关闭 / 全部打开**（总开关）、自动保活全局开关、参数（每段次数、前缀下限、人工轮次、凌晨时段、未命中冷却），解除未命中暂停；本期自动保活统计与「没开的原因」 |
| 会话列表 | 每个会话：缓存前缀与剩余倒计时、上次心跳、锁定 / 降级 / 异常提示、自动与长保活状态、计划进度。操作：**保活**（手动 N 次）、**立即补一次**、**停止**、**关闭自动 / 恢复自动**、**长保活 N 小时 / 取消长保活**、强制 |
| 保活执行记录 | 每段保活一行：心跳标记（✓ 命中、✗ 未命中、◐ 部分、⏱ 超时、! 失败）、花费、结局、收益、净；点行展开逐次心跳；可只看有结论的或包含进行中 / 没回来的 |
| 每日对比图 | 心跳成本 vs 保活节省，图 / 表切换 |
| 回测 | 用本机会话记录按当前规则重放，可展开参数对比 |
| 最近事件 / 冷启动重写 | 事件流；超过 TTL 的整段重写及当时自动保活为什么没开 |

## 长保活（pin）

给某个会话设一个到期时刻（默认 12 小时，最长 48 小时，`pin.defaultSec` / `pin.maxSec` 可改）：

```sh
cache-keepalive pin                 # 在任务的工作区（或 Paseo 任务内）执行，12 小时
cache-keepalive pin --for 24h       # 指定时长；--interval 45m 改间隔；--session 3d7c 指定会话
cache-keepalive unpin               # 取消；stop 也会取消
```

- 期间每段空闲（主对话最近一次真实请求之后）到间隔就发心跳，直到人回来或到期；会话继续了这段计划就结束，下一段空闲接着保。
  次数不受每段上限（12 次）限制，也不看自动保活的门槛（人工轮次、凌晨、前缀大小、Paseo 任务已关闭）。
- 不会多发：会话有请求在途不发；真实请求失败后 90s 内（客户端在重试）不发；工作期间只有真实请求没有心跳。
- 不会变贵：空闲已经超过 TTL−安全边际的那段不发（等下一次请求后接上，事件里记一次「超安全窗口」）；心跳没命中立即锁定并**取消长保活**；
  心跳有输出也取消；每日额度照常；Paseo 任务归档即取消；缓存已锁定的会话不能设。
- 与其他计划的关系：长保活接管后自动保活不再对该会话建计划；手动 `start` 的计划优先，结束后由长保活接上。
- 成本上界：整段时间都空闲时的心跳次数 × 单次读取费，`pin` 命令会打印；683K 的 Opus 会话 12 小时最多约 15 次 × $0.137 ≈ $2.0，对比一次整段重写 $5.46。

## 自动保活

每段空闲（主对话最近一次真实请求之后）在第一次心跳到点（50 分钟）时判定一次，符合条件就建一个自动计划，之后和手动计划
走同一套心跳、护栏与记账；会话一有新请求（人回来、工具执行完），这段的自动计划就结束，下一段空闲重新判定。

| 条件（默认值） | 说明 |
|---|---|
| 1h 缓存的主对话 | 子代理（带 `x-claude-code-agent-id`）、旁路请求、5m 缓存都不参与；请求标了 1h、上游却按 5m 写入时不参与 |
| 每段空闲最多 3 次 × 50m | 约覆盖 3.5 小时的离开；回测里 3 次净收益最高 |
| 缓存前缀 ≥ 100K tokens | 太小的会话省下的钱少 |
| 人工接入 ≥ 1 轮 | 没有人参与的自动化任务不保活；**停在 `tool_use`（工具、子代理、后台任务执行中）的空闲不看这一条**，它一定会有下一次请求（Paseo 显示任务已关闭时除外） |
| 1–8 点开始的空闲不保活 | 多半是去睡了，3.5 小时也保不住；熬夜到 1 点前离开的照常保活 |
| 任务进程已退出 | 这段空闲没人会回来；线上 7 天里「保活后没回来」13 段对「生效」10 段，没回来是最大的成本来源。判断方式见下；`auto set --skip-closed off` 关闭 |
| 中继错过判定窗口 | 空闲 50–58 分钟之间中继没运行（重启、停机）：缓存多半已过期，不发心跳，记为「错过判定窗口」，页面/CLI 不再显示「已就绪」 |
| 手动 stop / 页面「关闭自动」 | 整个会话不再自动保活，`auto on` / 页面「恢复自动」才恢复；`stop --global` 对当前所有会话执行同样的关闭 |
| 手动计划优先 | 有手动计划时不另建自动计划；这段空闲手动发过心跳后也不再自动保活 |
| 任务归档（Paseo） | 停掉进行中的自动计划，之后也不再开始 |
| 自动心跳没命中 | 锁定该会话，并全局暂停新的自动保活 2 小时（50 分钟时 1h 缓存没命中不正常，避免一连串整段重写） |

「任务进程已退出」怎么判断（`agentProbe`，两者都可关）：

- **进程探测（通用，Linux）**：扫 `/proc` 里的 Claude Code 进程（`claude` 或 `claude-code/cli.js`），先按命令行里的 `--resume` / `--session-id`
  精确匹配会话 ID，没带 ID 的按工作区匹配。只有「以前见过它的进程、现在找不到了」才判已退出；从没见过的（别的机器、容器、别的启动方式）返回未知，
  不影响保活。没有 `/proc` 的平台自动失效。
- **Paseo（可选）**：装了 Paseo 时优先用 `~/.paseo/agents` 里的任务状态与归档标记。

判定结果在 CLI 状态行、页面会话行与事件里都能看到（例如「本段空闲没有保活 — 缓存前缀 50K < 100K tokens」），
冷启动重写也会记下当时的判定，说明它为什么没被保住。参数可在页面「自动保活」卡片或 `auto set` 修改，写入 `config.json` 的 `auto`。

**回测**（`cache-keepalive backtest`、页面「回测」卡片）：读本机 Claude Code 的会话记录（`$CLAUDE_CONFIG_DIR` / `~/.claude` 的 `projects/`，
加上 Paseo 路由里标了 1h 的，`config.json` 的 `backtest.roots` 可再加目录），按线上同一个 `autoEligibility` 重放每段空闲，
节省按线上同一套冷启动口径计；心跳按全部命中计，回来时是否省钱看真实记录里那次请求有没有整段重写。
2026-10-22 用约 5 天的数据（34 个 1h 会话、51 段超过 50 分钟的空闲）回测默认规则：心跳 67 次 $4.78（白发 52 次 $3.38），
救回 9 次整段重写，省 $40.94，净收益 $36.17；不保活时这些空闲整段重写 15 次 $69.73，剩下的 6 次是凌晨开始的空闲和离开太久。
人工轮次 ≥ 2 会漏掉「发完第一条提示就离开」的会话（少救回 1 次 $2.22），所以默认 ≥ 1。

## 护栏（边界条件）

| 情况 | 处理 |
|---|---|
| 心跳没命中会话缓存：`cache_read=0`，或只读到前缀的一部分且重写超过 max(4096, 前缀 1%) | 立即停止并**锁定该会话**；没命中的那一发不算刷新，之后要等会话的下一次真实请求，再加 `--force` / 页面「强制」心跳命中才解锁。阈值从 5% 收紧到 1%：600K 前缀下 5% 允许 30K 重写（约 $0.24）仍算命中，会静默多付 |
| 心跳只读到部分前缀、写入不多 | 停止计划（前缀已变化） |
| 会话压缩（`/compact`、自动压缩、部分压缩） | 压缩请求照常记收益但不作为保活目标（压缩后旧前缀不会再被读到）；计划等压缩后的第一次请求，带来新前缀后继续 |
| 子代理请求（带 `x-claude-code-agent-id`） | 不作为保活目标，在途也不暂缓主对话的心跳。2.1.29x 的子代理同样带 Agent 工具，只看工具会把晚结束的子代理当成主对话 |
| 主对话识别 | 不是子代理，且带 Agent/Task 工具；或带 `x-claude-code-session-id` 的新版客户端里带任意工具的请求（`--tools` 限制、禁用 Agent、SDK 应用也能保活）。没有工具的标题生成/分类请求不算 |
| 距上次触达已超过 TTL − 安全边际（1h：58 分钟） | 不开启、不发送：缓存大概率已过期，心跳会变成整段重写 |
| 上一次请求 `cache_read + cache_write = 0`、没有 `cache_control` 断点 | 不能保活 |
| `thinking.type=enabled` | 不能保活（`max_tokens:0` 不接受；Opus 5.5 只有 adaptive，不会遇到） |
| 缓存前缀 < 50K tokens | 软护栏，需强制 |
| 会话有请求在途 | 暂缓心跳；真实请求本身会刷新缓存，计划自动顺延 |
| 中继重启 | 计划与账本保留；有进行中计划的会话快照随时落盘，缓存仍有效的主对话快照在优雅退出时落盘（自动保活接着发），重启后恢复；凭证按指纹借用之后经过中继的**同一把**凭证（只在内存） |
| 重启时有流式响应在途 | 优雅退出：先把热快照与状态落盘，再停止接新连接；已有 keep-alive 连接上的新请求直接 503（`x-should-retry: true`，Claude Code 退避重试到新进程，不转发上游）；只等退出前已在途的请求结束（最多 120s），在途心跳最多再等 60s，然后再落一次盘退出 |
| 改配置 | `config.json` 热加载（端口 / 上游除外），不用重启 |
| 中继不可用 | 路由启动任务时探测不到中继就直连 8080；中继恢复后下一次启动写回中继地址，运行中的会话随 settings.json 热切换 |
| 次数 / 间隔越界 | 1h：1–12 次、5m–55m；5m：1–10 次、1m–4m30s；超出按边界执行并提示 |
| 全局 | 每日最多 200 次 / $10，按每次心跳的预估花费预留（多个会话同时到点也不会一起越过上限）；计划最长 24 小时 |
| 真实请求失败（429/5xx/断开） | 客户端会立刻重试：之后 90s 内会话算活跃，不发心跳（`requestRetryGraceSec`） |
| 全局开始 / 停止 | `start --global` 逐会话跑同一套护栏，跳过原因汇总输出，不会因为某个会话失败而中断；`stop --global` 停全部计划并关闭全部当前会话的自动保活；`auto off --global` 只停自动计划 |
| 心跳有输出（上游没遵守 `max_tokens`） | 超过 16 个输出 token 就停发：每次心跳会按输出价（和思考）计费；该会话不再自动保活，手动需强制 |
| 请求标了 1h、上游按 5m 写入 | 按响应 usage 的 5m/1h 拆分识别：不自动保活，手动需强制（按 1h 间隔发必然不命中） |
| 调度出错 | 异常不吞也不让进程崩：计数并在 `health` 的 `stats.tickErrors` / `lastTickError` 里可见 |
| 网关不接受 `max_tokens:0` | 自动退回 `max_tokens:1` 重试一次（只多 1 个输出 token） |
| 网关/上游暂时不可用（连接失败、429、5xx） | 会话缓存多半还在：按 30s、60s、120s… 退避重试（封顶 5 分钟），重试到 TTL 安全窗口截止才停；真实请求回来时退避清零 |
| 心跳超时（默认 300s；实测 58 次 p50 5.6s / p90 16.6s / p99 94s / max 108s，原来的 120s 会被长上下文撞到） | 上游多半已经做完 prefill 并计费：记为「超时」，成本按读一遍前缀**预估**并计入账本与每日额度（页面/CLI 标「估」）；至少等 120s 再重试，连续两次超时告警 |
| 请求体超过 256MB | 中继要整段缓冲后再转发：直接 413，不转发不留快照（`maxBodyBytes`） |
| 心跳被拒（其他 4xx，如鉴权失败） | 30s 后再试一次，连续两次就停 |

心跳从「上次触达」（最近一次真实请求或命中心跳的**开始**时刻）起算间隔，用户继续工作时计划自动顺延，不会多发。

## 成本收益口径

- **心跳成本**：按心跳响应的真实 usage 计价（读取、写入、输出分别计）。
- **保活节省**：心跳后第一次真实请求（回来）若命中保住的前缀（读到最后一次命中心跳读到的 80% 以上；只读到约 23K 共享系统前缀不算），记 `前缀 × (写入价 − 读取价)`。
  仅当「回来时距上次真实请求 > TTL，且最后一次命中心跳仍在 TTL 内」才计入；TTL 内就回来时心跳算多余成本。
- **待兑现**：缓存正被保住、还没回来；按时回来能省的钱，尚未计入。
- **心跳命中率**：命中 ÷（命中 + 未命中）；网关/上游请求失败（退避重试会多发几次）不计入，单独列出。
- **分档计价**（Haiku 5.5 提示词超过 100K 整单高档）：按整条请求的提示词定档，不只看重写或保住的那部分。
- **冷启动可挽救**：分两列：按当前自动策略的每段次数（默认 3 次）能救回的，和手动用满次数上限（12 次）能救回的；隔夜 8 小时的空闲属于后者，自动策略救不到。只看主对话。距上一次请求超过它写缓存时的 TTL、期间没有心跳，并且旧前缀里有一大段没读到、被迫重写
  （超过 max(4096, 前缀 5%)），按默认间隔估算当时保活要几次心跳、能省多少；重写按这次请求实际的 5m/1h 写入单价计。
  压缩请求自己标 5m，读到之前 1h 的缓存不算冷启动；压缩后的第一次请求本来就是新前缀，也不算。

价格表在 `core.js` 的 `DEFAULT_PRICES`。网关有折扣或特殊计价时写 `~/.config/cache-keepalive/config.json`：

```json
{ "priceScale": 0.6, "prices": { "claude-opus-5-5": { "input": 4, "output": 20, "cacheRead": 0.2 } }, "minContextTokens": 50000,
  "alerts": { "webhookUrl": "https://open.feishu.cn/open-apis/bot/v2/hook/xxx", "format": "feishu" } }
```

配置文件不存在时全部走默认值，`cache-keepalive auto` 与页面会明确提示「配置文件不存在」，`auto set` / 页面保存会重新创建它。

其他可配项见 `core.js` 的 `DEFAULT_CONFIG`（端口、上游、TTL 参数、每日上限、`agentProbe`、`backtest.roots`、`pin` 等）；环境变量 `CACHE_KEEPALIVE_PORT` /
`CACHE_KEEPALIVE_UPSTREAM` / `CACHE_KEEPALIVE_STATE_DIR` 优先于配置文件。

## 数据与安全

- 请求体快照默认**只在内存**，不经 API 返回；总量上限 768MB，按最久未触达淘汰。
- 开启保活的会话，其快照写到 `~/.local/state/cache-keepalive/snapshots/`（目录 0700、文件 0600，**不含**
  `authorization` / `x-api-key` 等凭证头，只记凭证的 SHA-256 指纹前 16 位），计划结束即删除；优雅退出时缓存仍有效的主对话
  也会落盘，重启读回内存后即删除。内容与 Claude Code 自己的会话记录相同。
- 其余落盘只有 `state.json`（计划、会话元数据）、`ledger.jsonl`（心跳/回来/冷启动的 usage 与金额，保留 35 天）
  与 `relay.log`（中继日志，同时打到 stdout；启动时超过 5MB 轮转），均 0600。
- 中继只绑回环；控制 API 只认回环 Host（防 DNS rebinding），写操作要求 JSON 且同源（防跨站页面触发计费心跳）。
- 写操作（开启/停止/心跳/改设置）还要带 `x-cache-keepalive-token`，值在 `~/.local/state/cache-keepalive/control.token`（首次启动生成，0600）：
  同机其他用户、拿不到该文件的进程（如沙箱里的 agent）不能触发计费心跳或 `stop --global`。CLI 自动读该文件（或 `--token` / `CACHE_KEEPALIVE_TOKEN`），
  页面由中继注入。同一用户下的进程仍然拥有同等权限，这层只防误触和跨用户。`config.json` 设 `"controlToken": false` 关闭。
- 重启后恢复的快照不落凭证：优先借快照里记的同一把 token；同一会话 token 轮换后再来，也可以借它的新 token（同会话同账号）；别的会话的 token 不借。
- 告警：`config.json` 的 `alerts.webhookUrl` 配置后，未命中锁定、全局冷却、心跳连续超时、重启后等凭证、每日额度用尽、上游持续失败、调度异常会 POST 过去
  （`alerts.format: "feishu"` 用飞书自定义机器人格式；同类告警默认 10 分钟内只发一次）。

## 开销（实测）

中继要读完并解析请求体再转发，开销随请求体大小线性增长。本机假上游、与直连对照，每档 30 次（2026-10-22 加人工轮次识别后复测，`node cache-keepalive/bench.mjs 30 <会话记录.jsonl>`）：

| 请求体 | 增加的首字节延迟 p50 / p90 / max | 其中解析 p50 |
|---|---|---|
| 0.22MB（约 5 万 tokens） | 2.3 / 3.2 / 3.8ms | 1.2ms |
| 1.19MB（约 30 万 tokens） | 8.1 / 10.0 / 10.9ms | 6.1ms |
| 3.34MB（约 83 万 tokens） | 23.0 / 24.8 / 27.4ms | 18.8ms |

相对 Opus 秒级的首字延迟可以忽略。常驻内存：运行 14.5 小时、8 个快照时 RSS 117MB（单点，未做长期采样）。

## 真实会话验证中得到的结论

- **真实的未命中几乎不会是 `cache_read=0`**：Claude Code 的系统提示与工具定义（约 23K tokens）在同模型的会话之间共享，
  常被别的会话保活。会话自己的缓存过期后，心跳表现为「读到共享前缀 + 大量重写」，所以锁定条件同时看重写量。
- **压缩请求在主谱系上**：`/compact` 的请求与主对话同系统提示同工具，不识别的话会把作废的旧前缀当保活目标。
  1h 路由下压缩请求的断点仍是 5m：按它判断会把读到 1h 缓存的压缩请求误记成冷启动，冷启动改按上一次请求写缓存时的 TTL。
- **子代理同样带 Agent 工具**：本机路由的 general-purpose 子代理（走 Haiku）也带 Agent 工具，按工具判断会把它当主对话，
  它比主对话晚结束时保活目标就落到子代理上。改为看 `x-claude-code-agent-id`：子代理请求带，主线程不带（连自定义地址时
  Claude Code 不发 `x-claude-code-request-class`）。
- **上游故障时不能一失败就放弃**：一次网关上游整体不可用（18:40–20:00，全部模型 503 `no_account`）里，
  心跳 35 秒内连续失败两次就停了计划。改为对瞬时错误退避重试到安全窗口截止。
- **排空不能只停接新连接**：`server.close()` 后已有的 keep-alive 连接还会收新请求，带子代理的忙碌会话让在途数一直降不到 0，
  排空等满上限后把正在流式输出的请求一起切断（两次重启各切断了 1–2 个其他会话的请求）。改为排空期间新请求直接 503。
- **运行中的会话会热加载 settings.json 的 `env`**：路由改写地址后，同配置目录下正在跑的会话也会切换。
- 在 Paseo 任务里调用 `paseo run` 默认落在调用者的工作区，`--cwd` 不生效；脚本里起测试任务要去掉 `PASEO_AGENT_ID` / `PASEO_AGENT_CWD`。
